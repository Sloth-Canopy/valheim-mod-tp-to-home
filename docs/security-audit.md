# Security audit — Homeward 0.6.x

**Date:** 2026-09-22 · **Scope:** the mod as shipped in `dist/Homeward-0.6.0.zip` plus the fixes below · **Auditor:** Claude, with the owner reviewing

A BepInEx plugin runs with the same privileges as the game. This audit asks: given
that trust, what does Homeward actually *do* with it, and what can other players
do *to* a Homeward user through it?

## Threat model

| # | Who is at risk | From whom | Surface |
|---|---|---|---|
| T1 | The local player | The mod itself | Crashes/hangs, file or OS access, data collection |
| T2 | The local player | Other players on the server | The two routed RPCs the mod listens on |
| T3 | Other players | A Homeward user | Cheating, griefing, spoofing |
| T4 | Everyone | Supply chain | What's in the DLL, dependencies, reproducibility |

## What was checked

### Static sweep (T1, T4)
- Source grep for file, network, process, registry, environment, native and `unsafe` use: **none**. The only `System.IO` use is reading the two PNGs embedded in the DLL.
- Reflection: one call, `AccessTools.Method(typeof(Player), "StopEmote")` — a protected game method, invoked only on the local player.
- Harmony patches (3): `Player.OnDamaged` (postfix, sets a flag, local player only), `Player.ShowTeleportAnimation` (prefix, local player only, only during our own teleport), `Hud.UpdateActionProgress` (postfix, only while the local channel is active). No transpilers. Nothing patched on the server path.
- NuGet packages: **none**. References: BepInEx, 0Harmony, `assembly_valheim`, `assembly_guiutils`, `netstandard`, and five `UnityEngine` modules (Core, Audio, ImageConversion, ParticleSystem, Physics). No `System.Net`, no `UnityEngine.Networking`.
- Strings in the DLL: no URLs. No telemetry, no analytics, no update check.
- Data written: one key in `Player.m_customData` (`homeward.lastUsed`, a unix timestamp) inside the game's own character save. Nothing else touches disk.
- Log output: BepInEx log lines with positions of the local player's bed/teleport target. Local file only.
- Reproducible: `dotnet build -c Release` from this repo produces the shipped DLL. Textures and icon are generated by `tools/gen_textures.py`.

### Network input (T2)
The mod registers two routed RPCs, `Homeward_ChannelStart(ZDOID who, Vector3 pos, string style)` and `Homeward_ChannelStop(ZDOID who)`. Any peer can send them.

### Abuse potential (T3)
The mod never sends chat, never moves, damages or affects another player, and its RPCs only draw a cosmetic ring. `AllowWithMetal` lets a user bypass the portal metal rule **for themselves** — a client-side choice, like many QoL mods; it cannot be enforced server-side without ServerSync (decision #20).

## Findings

| ID | Severity | Finding | Fix |
|---|---|---|---|
| F1 | **Medium** | **No sender authentication on RPCs.** A modded peer could send `ChannelStart` with any `ZDOID` and any position — placing rings anywhere, attributed to anyone. Cosmetic, but spoofable. | `Validate()`: the routed-RPC sender id is the same session id ZDO ownership uses (`ZNet.cs:385`), so we now require `ZDOMan.GetZDO(who).GetOwner() == sender`, and the claimed position to be within 4 m of that object's real position. |
| F2 | **Medium** | **Unbounded resource use from the network.** Each `ChannelStart` with a fresh `ZDOID` created a new GameObject with a particle system and kept it in a dictionary — a spammer could degrade a client's frame rate and memory. | Cap of 12 concurrent rings from others, per-sender rate limit (1 start / 0.5 s), rings beyond 200 m rejected, 30 s TTL already existed. |
| F3 | **Low** | **Exceptions in RPC handlers propagate into the game's RPC dispatch.** A malformed payload that threw would surface as an error in the game's network loop. | Both handlers wrapped in try/catch; failures logged with the sender id. |
| F4 | **Low** | **Non-finite / oversized payloads not rejected.** NaN/Infinity positions, arbitrarily long style strings. | Rejected in `Validate()`: finite check, `style` ≤ 32 chars. Radius was already clamped to 0.3–5. |
| F5 | **Low** | **A future `homeward.lastUsed` timestamp** (clock change, edited save) could lock the player out for longer than one cooldown. | Clamped to "now" on read. |
| F6 | **Low** | **An exception in the plugin's `Update` would log at frame rate** and could block hotkey handling. | `Update` wrapped; errors logged at most once per 5 s. |
| F7 | Info | `AllowWithMetal` is a self-only cheat toggle. | By design; documented in the package README. Server enforcement deliberately out of scope (decision #20). |
| F8 | Info | Rings for the local player skip validation. | Intended: they come from our own code path in-process; validating would only add a failure mode. |
| F9 | **Low** | **Build-machine path embedded in the DLL** (`/home/<user>/projects/.../Homeward.pdb`) — discloses the developer's OS username. *Found by the external screening, missed here.* | Release builds now set `DebugType=none`, `Deterministic=true` and `PathMap` to a neutral root. Verified: `strings Homeward.dll` contains no `/home/`, username, or `.pdb`. The 0.6.1 zip that was already shared does contain it. |

## External screening (ChatGPT Codex, 0.6.1 package)

An independent binary/string-level screening of the shipped 0.6.1 zip (report kept
locally in `docs/external/`, not published) found no high-severity behaviour and
one new item, F9 above. It also listed nine points a source review must verify
for the RPC path. Mapping them to the code (`src/ChannelNet.cs`):

| # | Codex asks | Where it's true |
|---|---|---|
| 1 | Sender identity can't be spoofed | The sender id is supplied by the game's routed-RPC layer from the peer connection, not from the payload. |
| 2 | A client can't claim another player's identity | `Validate`: `ZDOMan.GetZDO(who).GetOwner() == sender`. |
| 3 | Position threshold is strict | `MaxPosDrift = 4 m` from the claimed player's real ZDO position. |
| 4 | NaN/Infinity and unreasonable coordinates rejected | Finite check on x/y/z; `MaxDrawDistance = 200 m` from the local player. |
| 5 | Rate limit keyed to an authenticated sender | `_lastStartBySender` is keyed by the game-supplied sender id, after ownership passes. |
| 6 | Ring cap can't be bypassed by changing identifiers | `MaxOtherRings` counts live ring objects, not ids; ids must be ZDOs the sender owns. |
| 7 | TTL enforced without a Stop | `RingTtlSeconds = 30` on every ring from another player (`ChannelVfxBehaviour.Update`). |
| 8 | `RpcStop` can't remove someone else's ring | `OnStop` runs the same ownership check: you can only stop a ring for a ZDO you own. |
| 9 | Malformed input can't destabilise the game loop | Both handlers and the plugin `Update` are wrapped in try/catch; failures are logged, throttled. |

## Residual risk (accepted)
- A peer who *does* own a ZDO (their own player, a dropped item) can draw a ring at that object. Cosmetic, capped, rate-limited, fades in 30 s.
- Any BepInEx mod can do anything the game can; users should install mods only from sources they trust. Homeward is open source so that trust can be checked.
- No code signing (Thunderstore doesn't support it). Verify by building from source.

## Verification
- Build after fixes: 0 warnings, 0 errors.
- Manual re-test to do in-game: rings still appear for a friend (validation must not reject legitimate starts — note the 4 m position tolerance vs. latency), stop still works, own ring unaffected.

## Re-audit triggers
Re-run this audit if the mod ever: adds an RPC or changes a payload; reads or writes files; adds a dependency; patches anything on the server path; adds ServerSync.
